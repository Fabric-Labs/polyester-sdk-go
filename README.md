# Polyester Go SDK

Go SDK for the Polyester API with generated protobuf types and ConnectRPC clients.

Official Go SDK for Polyester APIs, built for trading bots, backend services,
and automation. Parity with `polyester-sdk-python` and `polyester-sdk-rust`
using the checked-in `gen/` protobuf bundle (no local proto generation for
normal development).

**Status:** `v0.8.0`, pre-1.0: a minor release may change the API. The Go,
Python and Rust SDKs are released together. Their versions match unless a
change breaks only one SDK's API: Go `v0.8.0` is the release of Rust `0.9.0`.
Proprietary license (not open source).
API-key only; no browser login or session MFA.

Requires a recent Go toolchain (see `go.mod`).

Address-book writes (`CreateEntry` / `UpdateEntry` / `DeleteEntry` and tag
create/update/delete) are wrapped. `new_tags` creates and attaches tags in the
same protected update; when `tag_ids` is omitted, current tags are preserved
and the new tags are appended. `GetView(..., minimumViewRevision)` omits the
revision when it is 0; the view and invalidation payloads include
`view_revision`. Twitter social-verification handles accept an
optional leading `@` and are forwarded as-is.

Rows marked **Yes** mean that an SDK wrapper exists; deployment authorization
still applies. In particular, social-verification and address-book writes may
require a JWT session or may not be mounted.
Private streams require an Account ID and the corresponding API-key permission.
For Centrifugo channels, a successful subscribe call means the token exchange
and realtime handshake completed. `Orders.Subscribe` returns at once and reports
the handshake as events (see [Realtime](#realtime)). Treat a structured
permission denial as non-transient and update the API-key policy before retrying.

**Attached risk:** set `CreateOrderRequest.AttachedRisk`,
`ModifyParams.NewAttachedRisk` (`Orders.ModifyWith`), or
`BatchReplaceItem.NewAttachedRisk` to a `models.AttachedRiskInput` with a
take-profit and/or one stop leg (stop-loss or trailing stop); `OCO: true`
requires a take-profit and a stop leg. A leg without `LimitPrice` exits with a
market child; with `LimitPrice` it rests a GTC limit child. A trailing stop
on a sell order buys back, so `TrailingStopInput.LimitPrice`, the most its exit
pays per unit, is required there (at least `ActivationPrice` when set); a buy
order's trailing stop takes none. A modify replaces
the order's whole attached policy. Create and modify results carry the
configured legs' trigger IDs. When requested, each decoded leg exposes typed
runtime `State` (`Status`, nanosecond armed/terminal timestamps, `TriggerID`,
and `ChildOrderID`). A leg is retained when it has meaningful runtime state or
a usable policy (positive TP/SL trigger price or positive trailing distance);
empty/malformed policy wrappers are omitted. State-only responses leave policy
fields empty. Valid stop loss and trailing legs are both retained together.
A buy sized by a quote amount (`MaxQuoteDebitScaled`) takes attached risk too:
the server checks each leg against the pair's minimums at the quantity the
amount buys at the order's price limit, and the legs then protect what the
fills bought.

Attached exits never trade with the order they protect. When a leg fires
while its order still rests, the order's unfilled rest is canceled first
(`CancelReason` `attached_exit_fired`; earlier fills stand). The order's
`CreateOrderRequest.SelfTradePreventionMode` (`expire_maker`, the default,
`expire_taker` or `expire_both`) also applies to its attached exits' orders.
When self-trade prevention expires one of those against another of the
account's resting orders, the leg stays `armed` and its trigger records one
`fire_refused` event with `FireRefusalReason` `self_trade_prevented`.
`Order.SelfTradePreventionMode` reads the mode back.

## Quick start

Create an API key in the Polyester app (**API** in the sidebar). Copy the key id
and private key when shown. The private key is only displayed once.
Open the key's **Permissions**, enable **Spot trading**, select the markets it
may trade, and set a maximum order size appropriate for the strategy.

Subaccount-scoped keys also need an attached **API-key policy**. Grant ledger
read permission for balance reads and private balance streams, and grant
trading permission for order mutations. This key policy is separate from the
subaccount policy; authorization applies the intersection of both.

```go
package main

import (
	"context"
	"fmt"
	"log"

	polyester "github.com/Fabric-Labs/polyester-sdk-go"
)

func main() {
	accountID := "YOUR_ACCOUNT_ID" // Profile → Account ID
	client, err := polyester.New(polyester.Config{
		Environment:      &polyester.DevnetEnvironment,
		APIKeyID:         "ak_...",
		APIPrivateKey:    "...", // 64-char hex secret from API key creation
		DefaultAccountID: &accountID,
		HydrateCatalogs:  true,
	})
	if err != nil {
		log.Fatal(err)
	}
	defer client.Close()

	ctx := context.Background()
	overview, err := client.MarketOverview.List(ctx, nil, 5, "", false)
	if err != nil {
		log.Fatal(err)
	}
	for _, market := range overview.Markets {
		fmt.Println(market.Symbol, market.LastPrice.Ticks(), market.IndexPrice.Ticks())
	}

	openOrders, err := client.Orders.ListOpen(ctx, nil, nil, nil, nil, false, false, nil)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("%d open orders\n", len(openOrders.Orders))
}
```

## Credentials

| Value | Where to find it | Config field |
| --- | --- | --- |
| API key id | **API** → create or view key | `APIKeyID` |
| API private key | Shown once when the key is created | `APIPrivateKey` |
| Account ID | **Profile** → **Account ID** | `DefaultAccountID` |

Pass credentials on `polyester.Config` / `polyester.New`. The SDK does not
implicitly read environment variables unless you call `FromEnv`.

`APIPrivateKey` accepts the 64-character hex Ed25519 secret from key creation,
or raw 32-byte key material via the credentials loader.

`DefaultAccountID` is the **Account ID** string from your Profile page. Use the
value exactly as shown in the app. Do not use an internal numeric id.
Username is optional; API-key authentication with the Account ID is valid.

`DefaultAccountID` is optional for public market-data calls. It is required for
account-scoped operations such as private realtime channels, bucket transfers, and
some ledger writes.

Automatic request signing gives concurrent identical calls distinct authentication tuples.
Credential copies for the same key share the process allocator. Timestamps can lead the local clock
by at most five seconds; larger bursts are backpressured instead of reusing a signature or drifting
outside the API's 10-second freshness window.

Recognized retry-later Connect `resource_exhausted` and REST admission-limit responses map to `errors.RateLimitError`. When the
server attaches `polyester.ratelimit.v1.RateLimitDetail` (top-level Connect detail or nested under
`orders.v1.ErrorDetail.rate_limit`), use `RateLimitError.Detail` for `policy_class`, `scope`,
`operation_id`, and presence-aware quota fields. `RetryAfter` prefers `detail.retry_after_ms`,
then `Retry-After` / `Retry-After-Ms` / `Grpc-Retry-Pushback-Ms` headers. Preview and batch
rejections expose the same payload on `OrderErrorDetail.RateLimit` / batch item `RateLimit`.
That error payload is distinct from `client.RateLimits` (`ratelimit.v1.RateLimitService`),
which returns the public trading quota catalog and authenticated account / API-key limits.
Canceled/deadline failures map to `errors.TransportError`; Connect validation
codes map to `errors.ValidationError`. Structured order violations preserve the
order code plus field/rule/message metadata on `ValidationError`.

## Authentication patterns

**Recommended: explicit config**

```go
accountID := "YOUR_ACCOUNT_ID"
client, err := polyester.New(polyester.Config{
	APIKeyID:         "ak_...",
	APIPrivateKey:    "...",
	DefaultAccountID: &accountID,
	HydrateCatalogs:  true,
})
```

**If your deployment stores secrets in environment variables**, read them in your
application and pass them to `New`:

```go
accountID := os.Getenv("POLYESTER_ACCOUNT_ID")
client, err := polyester.New(polyester.Config{
	APIKeyID:         os.Getenv("POLYESTER_API_KEY_ID"),
	APIPrivateKey:    os.Getenv("POLYESTER_API_PRIVATE_KEY"),
	DefaultAccountID: &accountID,
	HydrateCatalogs:  true,
})
```

`polyester.New` never implicitly reads `os.Environ`.

`Config.APIURL` must be an absolute `http` or `https` base URL. Paths (including
local `httptest` server paths) are supported, but query/fragment delimiters
(including bare `?` or `#`) are rejected before any Connect client or signing
URL is constructed. Percent-escaped `?` / `#` path content remains valid.
HTTP(S) proxy bases may include URL userinfo; `Config.String` and `GoString`
omit URL userinfo and replace malformed URLs with a neutral placeholder so
credentials are not exposed in formatted configuration.

Pass `Config.Environment` so API, websocket, RPC, and contract pins stay
together. `DevnetEnvironment` is the `New` default. `TestnetEnvironment` targets
public testnet (`api.testnet.polyester.com`, chain `888169`). Custom / VPC
endpoints use `CreateEnvironment` or `Environment.WithURLs`. `APIURL` / `WSURL`
remain as transport overrides.

**Scripts and local tests only:** `polyester.FromEnv()` loads
`POLYESTER_API_KEY_ID`, `POLYESTER_API_PRIVATE_KEY`, optionally
`POLYESTER_ACCOUNT_ID`, `POLYESTER_ENV=devnet|testnet`, and optional
`POLYESTER_API_URL` / `POLYESTER_WS_URL` overrides. This is a convenience
helper, not the primary integration pattern.

`FromEnv` enables spot and Zipper catalog hydration. The zero value used by
`New` disables it, so set `HydrateCatalogs: true` explicitly when using decimal
writes that depend on catalog scales. Wait for hydration before those writes:

```go
if err := client.WaitForCatalogs(ctx); err != nil {
	log.Fatal(err)
}
```

`WaitForCatalogs` returns immediately when `HydrateCatalogs` is disabled. When
hydration is enabled, it returns an error if spot/Zipper hydration failed or
catalogs are unusable (use `CatalogsLastError()` to inspect). Typed Zipper
hydration is available via `client.Catalogs.HydrateZipperConfig(cfg)` /
`HydrateDepositWithdrawConfig`. Hydration rejects ancillary struct values with
unexported fields: generic raw snapshots must be JSON-shaped rather than
lock/no-copy-bearing Go values. `time.Time` is the explicit immutable exception;
ordinary maps, slices, pointers, cycles, and JSON-compatible aliases remain
supported.

Public methods may still accept display `symbol` strings. The SDK resolves them
through the spot catalog and fails closed on unknown symbols. Connect requests
send `symbol_id` only (GetSpotConfig still accepts both). Empty or omitted
symbol filters mean all symbols (`symbol_id = 0`). Use
`Catalogs.PairConstraintsForSymbol` (or `PairConstraintsForSymbolID`) to inspect
tick size, quantity step, minimums and order limits; order admission stays
server-side.

`MarketData.GetSpotConfig` returns a typed `models.SpotConfig`: `Assets`,
`Pairs` (symbol, IDs, scales, tick and step size, minimums, status labels such
as `halted`, default slippage) and the order limits. `MaxLimitQtyBase`,
`MaxMarketQtyBase` and `MaxOrderNotionalQuote` are decimal strings, empty when
the pair has no maximum; larger orders are rejected with `ERROR_CODE_MAX_QTY`
or `ERROR_CODE_MAX_NOTIONAL`. `MaxMarketNotionalQuote` caps one market
order's notional, valued at a buy's protection price or a sell's reference
price (empty means no cap, not zero). `MaxOpenOrdersPerPair` and the config's
`MaxOpenOrdersTotal` are the venue's default resting-order limits for a
typical account (an account may have a lower one); zero when not published. A
malformed response is an error, never an empty config. `SpotConfig.Raw` is the
proto-JSON payload `Catalogs.HydrateSpotConfig` accepts. Hydrated catalogs
expose the same limits on `PairConstraints` (with scaled base quantities) and
`Catalogs.MaxOpenOrdersTotal()`.

```go
cfg, err := client.MarketData.GetSpotConfig(ctx)
if err != nil {
	log.Fatal(err)
}
for _, pair := range cfg.Pairs {
	fmt.Println(pair.Symbol, pair.Status, pair.MaxLimitQtyBase, pair.MaxOpenOrdersPerPair)
}
if limits, ok := client.Catalogs.PairConstraintsForSymbol("BTC-USDT"); ok {
	fmt.Println(limits.MaxMarketQtyScaled, limits.MaxOrderNotionalQuote)
}
```

Scaled bot inputs (`PriceFromTicks`, `QtyFromScaled`, `AssetAmountFromScaled`)
must carry their source scale. An `AssetAmount` constructed without scale is
accepted for composition only and fails closed on transfer/withdraw encoding
unless the request's `amount_scale` / `quantity_scale` is explicit. Prefer
`AssetAmountFromDecimal`, or attach `.WithScale(scale)` before encoding.

## Create and cancel orders

```go
import "github.com/Fabric-Labs/polyester-sdk-go/models"

symbol := "BTC-USDT"
tif := "gtc"
clientOrderID := "my-bot-001"
price := models.PriceFromDecimal("100")

result, err := client.Orders.Create(ctx, models.CreateOrderRequest{
	Symbol:        &symbol,
	Side:          "buy",
	OrderType:     "limit",
	TIF:           &tif,
	Qty:           models.QtyFromDecimal("0.01"),
	Price:         &price,
	PostOnly:      true,
	ClientOrderID: &clientOrderID,
}, nil)
if err != nil {
	log.Fatal(err)
}
fmt.Println(result.Status, result.OrderID)

_, err = client.Orders.Cancel(ctx, nil, models.OrderKeyByClientID(clientOrderID), &symbol, nil, nil)
```

An order read says why the order ended. A `rejected` order's `RejectReason`
names its refusal as the order write API does, for example `POST_ONLY_CROSS`
or `INSUFFICIENT_FUNDS` (the `ERROR_CODE_` name without its prefix). A
`canceled` order's `CancelReason` is one of `user_request`, `ioc_remainder`,
`market_remainder`, `stp_expire_maker`, `stp_expire_taker`, `stp_expire_both`,
`replaced`, `gtd_expired`, `qty_at_or_below_filled`, `pair_drain`,
`attached_risk_refused`, `cancel_all_after`, `account_repair`,
`twap_rollover`, `strategy_cancel`, `market_halted`, `attached_exit_fired`
(its take-profit, stop-loss or trailing stop fired while it still rested) or
`system`. Both are empty for every other
status. A value newer than this SDK decodes as `UNKNOWN_ERROR_CODE(N)` or
`unknown(N)`; treat it as a generic refusal or cancel.

`ClientOrderID` is **optional** (matches the API). Omit it for one-shot creates.
**Set a stable non-empty value when you may need to reconcile** after an
ambiguous transport/server failure. Without it you cannot tell whether the
first attempt admitted the order. After an unknown outcome, look up that id
(`Get` / `ListOpen`) before creating again. A second create with the same id
is rejected (`CONFLICT_DUPLICATE_CLIENT_ORDER_ID`) even when the payload
matches. Only create again with that id if reconciliation shows the first
attempt did not admit.
A create, cancel or modify that the server sent but could not confirm in time
fails with `ERROR_CODE_ORDER_CREATE_OUTCOME_UNKNOWN`,
`ERROR_CODE_ORDER_CANCEL_OUTCOME_UNKNOWN` or
`ERROR_CODE_ORDER_MODIFY_OUTCOME_UNKNOWN`, a trigger create with
`ERROR_CODE_TRIGGER_CREATE_OUTCOME_UNKNOWN`, and a trigger cancel, pause,
resume or modify with `ERROR_CODE_TRIGGER_CONTROL_OUTCOME_UNKNOWN`: the change
may still apply.
For every order error code ending in `_OUTCOME_UNKNOWN`,
`errors.MutationOutcomeUnknown` reports true and `errors.IsRetryable` reports
false: read the order or trigger back (by client order ID or client trigger
ID) before sending it again.

The retry flag is always false when the mutation outcome is unknown. This includes
bare Connect `unavailable`, `internal` and `deadline_exceeded`, gateway 502/503
bodies, bare or HTML 429 responses and client timeouts. Read back after an unknown outcome; retry reads explicitly. Automatic
trigger reads, status waits and snapshot refresh use read context and can retry these
failures within their existing budgets. Creates are never automatically resent.

A typed `orders.v1.ErrorDetail` carrying `UNAVAILABLE` proves a known, retryable
orders refusal. A bare REST `UNAVAILABLE` or a Connect message with only that
name does not establish its source: outcome unknown and non-retryable. Specific
refusals such as `FEE_SCHEDULE_UNAVAILABLE`, `POLICY_UNAVAILABLE` and
`RATE_LIMIT_POLICY_UNAVAILABLE` are known and retryable on typed Connect,
code-only Connect messages and recognized REST 503 problems. A REST 502 cannot
establish these refusals. `ACCOUNT_ROUTING_INVALID` means the trigger was not
admitted; contact support if it persists.

`RATE_LIMIT_EXCEEDED`, `PRICE_LEVELS_EXHAUSTED` and retry-later capacity codes
are known, retryable admission refusals; preserve and respect any server delay.
The additional retry-later codes are:

- `CLIENT_ORDER_IDS_EXHAUSTED`
- `CLIENT_ORDER_ID_CAPACITY_REACHED`
- `MARKET_LADDER_LIMIT_EXCEEDED`
- `MARKET_TRIGGER_LIMIT_EXCEEDED`
- `MARKET_TWAP_LIMIT_EXCEEDED`
- `NEW_ACCOUNT_CAPACITY_REACHED`
- `REQUEST_RECEIPTS_EXHAUSTED`
- `RESERVATION_CAPACITY_REACHED`
- `TRIGGER_CAPACITY_REACHED`
- `TRIGGER_CONTROL_SHARE_EXHAUSTED`
- `TWAP_CAPACITY_REACHED`

These behave the same on REST, typed Connect and code-only Connect messages.
The resource codes without retry guidance are `ORDER_SEQUENCE_EXHAUSTED`,
`TRIGGER_FIRE_LIMIT_REACHED`, `QUICKSWAP_CAPACITY_REACHED`,
`ACCOUNT_RESERVATION_LIMIT_REACHED` and `TRIGGER_LIMIT_EXCEEDED`: outcome known,
non-retryable, including message-only responses.

A plain REST gateway 504 returns `*errors.ServerError` with `Status == 504`:
`errors.IsRetryable` is false and `errors.MutationOutcomeUnknown` is true.
The classifier has no operation context. Reads may retry a 504 explicitly;
writes read back first. A client order ID supports reconciliation, not exact
replay of a single create. Without one, read open orders before deciding whether
to submit again. The SDK never automatically resends a create; trigger/status
reads and snapshot recovery keep their own safe read retries.
`OVERLOADED` and `SYSTEM_RATE_LIMITED` are retryable admission refusals on
Connect and REST, with no unknown mutation outcome. Respect `RetryAfter` when
supplied. Branch on `RateLimitError.Code`: `ERROR_CODE_OVERLOADED` means wait for an
outstanding request to complete; `ERROR_CODE_SYSTEM_RATE_LIMITED` names a venue-wide limit.
`ORDER_SEQUENCE_EXHAUSTED` is permanent; contact support instead of retrying.
On REST outcome-unknown and refusal errors (including HTTP 400, 409, 412 and 422),
`APIError.Problem` retains code, actual HTTP status, canonical type and detail.

`ERROR_CODE_ACCOUNT_REPAIRING` and `AUTH_TEMPORARILY_UNAVAILABLE` changed
nothing and `errors.IsRetryable` reports true: retry the same request shortly.
`errors.TimestampSkewError` (`TIMESTAMP_SKEW`) means the API-key signature
timestamp fell outside the server's window, for example after waiting in a
large concurrent burst or with a drifting clock. It changed nothing and is
retryable: a retry signs again. Bound concurrency or fix the clock if it
recurs. `errors.NotImplementedError` (Connect `unimplemented`, or a contract
code at HTTP 501) means the server does not offer the operation; retrying does
not help. An HTTP error with no code the contract defines can come from a gateway
or an edge, so it doesn't prove a request was refused. Only a 401 or 403 is a
refusal on its status alone (`errors.AuthError`). Every other status returns
`errors.ServerError` with `errors.MutationOutcomeUnknown` true and
`errors.IsRetryable` false, and keeps any code it did send in `Code`; read back
before sending a mutation again. Reads retry 429, 502, 503 and 504 for you. A
bare 404 stays `errors.RouteNotFoundError`, also with an unknown outcome. A
well-formed but unrecognised code at HTTP 429 returns `errors.APIError`: known
and not retryable.
`errors.AuthErrorCode(err)` names why credentials or a session were refused,
the same way for both transports: it reads the Connect
`auth.v1.AuthErrorDetail` code and a REST problem `code` with the `AUTH_`
prefix added (`UNAUTHENTICATED` reads `AUTH_AUTHENTICATION_REQUIRED`). An
API key refused by order reads, order and trigger writes or balance reads is
an `*errors.AuthError` whose code is one of `errors.AuthCodeSignatureInvalid`,
`AuthCodeMissingHeaders`, `AuthCodeKeyExpired`, `AuthCodeKeyDisabled`,
`AuthCodeIPNotAllowed` or `AuthCodeAPIKeyNotAccepted`; none is retryable
without a change by the caller (fix the signature, the key, or the calling
address). `AUTH_TIMESTAMP_SKEW` is the retryable `errors.TimestampSkewError`
above, from either transport.

```go
switch errors.AuthErrorCode(err) {
case errors.AuthCodeTimestampSkew:
	// Retry: the SDK signs again with a fresh timestamp.
case errors.AuthCodeIPNotAllowed:
	// Call from an address on the key's allowlist.
}
```

`errors.SessionRequiredError` (`AUTH_SESSION_KIND_NOT_ALLOWED`, Connect
`permission_denied` or REST 403, "interactive session required") refuses an
API key on a method that accepts only a session token, on every service:
withdraw and auto-withdraw rule writes, portfolio equity reads, VIP status,
checkpoints and guard signer methods. `errors.IsSessionRequired` tests for
it; it changed nothing and is not retryable with an API key. It unwraps to
`*errors.APIError`, so a direct type assertion to `*errors.APIError` no longer
matches it. A withdraw-service refusal of an API key whose policy lacks an
action keeps its server message, which names the action to grant, for
example "api key policy does not allow READ_AUTO_WITHDRAW".

Order refusals name the fields to fix: `errors.Violations(err)` returns the
`errors.FieldViolation`s (`FieldPath`, `RuleID`, `Message`) of a
`*errors.ValidationError`, from the order `ErrorDetail`, from request
validation (`buf.validate.Violations`) or from a REST problem's
`violations`. Paths are those of the transport that answered: Connect names
proto fields (`order.base_qty_scaled`), REST its JSON fields
(`order.baseQty`). Branch on the code, and on `RuleID` within it.
`models.OrderFieldViolation` in preview and batch results is the same type.

`errors.SubaccountOwnerRoleLockedError` (`AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED`,
Connect `failed_precondition` or REST 412) refuses a sub-account member call
that targets the sub-account's owner: inviting the owner, accepting an invite
granted to the owner, changing the owner's role or removing the owner. It
changed nothing and is not retryable; `errors.IsSubaccountOwnerRoleLocked`
tests for it, and `errors.AuthErrorCode` still reads its code. Show "The
owner's role can't be changed", and don't offer these actions for the member
whose role is `OWNER`.
Client order ids accept 1 to 36 ASCII letters, digits, `.`, `_`, `:`, `/`, and
`-`. Batch create, cancel, and replace accept at most 20 items (rejected locally
before encoding). `BatchCreate` always sends `request_id` (caller value or a
generated `batch-create-*` key); that batch-level id is the idempotency
boundary, so per-item `ClientOrderID` may be omitted. Duplicate non-empty
per-item client order ids in one batch are rejected locally. Treat a cancel response as an admission acknowledgement and
reconcile with `ListOpen` before releasing local state.

`Orders.CancelAll` returns `CancelledOrders` (order ID and client order ID),
the orders whose cancellation was requested, oldest first and at most 200,
with `TotalCancelled` and `Truncated` when more were canceled. Each moves to
`canceled` asynchronously; the order stream and order reads report every
one. A dry run lists none. Retrying with the same request ID within 120
seconds returns the original status and counts with an empty
`CancelledOrders` and `ListingStatus` `not_retained_read_open_orders`
(`included` otherwise): the empty list does not mean nothing was canceled.
Read open orders for current state. `Orders.CancelAllAfter` reports the
armed switch's scope as `EffectiveScope` (nil when disabled).

`Orders.CancelAll` and the dead-man switch (`Orders.CancelAllAfter`) cancel
open orders, never triggers. The open orders triggers placed (a TWAP's
working slice, a ladder's levels, a fired stop's order, an attached leg's
working exit) are canceled like any other, but untriggered stops stay armed,
TWAPs keep running and paused triggers stay paused, with their reserved
funds. `MatchedOrders` counts orders only. `client.StopAllTrading(ctx,
account, services.StopAllTradingScope{...})` stops all automated trading in
scope: it lists the live triggers (created, armed, running, paused, every
page), cancels each, then cancels all orders, in that order so an order a
trigger places before its cancel is still canceled. A failed trigger cancel
is listed in `FailedTriggers` and returned as an error after the cancel-all.

A cancel of an order that has already ended, a repeat of the cancel that
ended it included, fails with `ERROR_CODE_ORDER_ALREADY_TERMINAL`:
`errors.IsOrderAlreadyTerminal(err)` reports it. Treat it as already done and
read the order for how it ended. A retry by client order ID more than a
minute after the order ended may read `ERROR_CODE_ORDER_UNKNOWN`, so cancel by
order ID once you have it. Every cancel, repeats included, counts against
the cancel rate limit.

Use **decimal strings** for human-facing `qty` / `price` inputs. Do **not** pass
floats. `PriceTicks.Ticks()` returns Polyester protocol price units (fixed 1e9),
not market tick-size alignment (server validates tick size).
Pagination `limit` values never wrap during protobuf conversion: zero preserves
each method's documented omitted/default behavior, while negative or uint32-
overflowing explicit values return `errors.ValidationError`.

### For bots (scaled integers)

Stay in integer space; no string round-trip:

```go
scale, ok := client.Catalogs.BaseQuantityScaleForSymbol(symbol)
if !ok {
	log.Fatal("base quantity scale is unavailable; wait for hydrated catalogs")
}
qty := models.MustQtyScaled(1_000_000).WithScale(scale).WithSymbol(symbol)
price := models.PriceFromTicksInt(100_000_000_000) // 100.000000000 at 1e9
_, err = client.Orders.Create(ctx, models.CreateOrderRequest{
	Symbol: &symbol, Side: "buy", OrderType: "limit", TIF: &tif,
	Qty: models.QtyFromScaled(qty), Price: &price, PostOnly: true,
}, nil)
// Reads expose immutable getters: order.Price.Ticks(), order.OrigQty.Scaled()
// OrigQty is the current accepted total and changes after a successful modify.
```

Compatible values from fills/books can be passed back into writes when the
instrument/domain matches. Transfers and trading withdraws use
`AssetAmountInput` (not order `QtyInput`).

### Quote-budget orders and previews

Create requests use exactly one sizing mode: base `Qty`, or
`MaxQuoteDebitScaled` (a typed hard all-in quote-debit budget). Construct the
latter with `QtyFromQuoteDecimal` / `QtyFromQuoteScaled`; the SDK validates its
`OrderQuote` domain and scale against
`Catalogs.QuoteQuantityScaleForSymbol`. Quote-budget sizing is valid for BUY
market and limit-IOC orders. `FeeAsset` is `quote` (default) or `base`; base
fees are valid for BUY orders only. The former `received` fee source is now
`base`.

```go
quoteScale, ok := client.Catalogs.QuoteQuantityScaleForSymbol(symbol)
if !ok {
	log.Fatal("quote quantity scale is unavailable; wait for hydrated catalogs")
}
budget := models.QtyFromQuoteDecimal("25.00")
// or: models.QtyFromScaled(models.MustQtyQuoteScaled(25_000_000, quoteScale).WithSymbol(symbol))
_, err = client.Orders.Create(ctx, models.CreateOrderRequest{
	Symbol: &symbol, Side: "buy", OrderType: "market",
	MaxQuoteDebitScaled: budget,
}, nil)
```

Use `client.Orders.Preview(ctx, request, account)` with the same
`CreateOrderRequest` shape as create. On the wire, preview wraps a full
`OrderIntent` (same contract as `CreateOrderRequest.order`) and returns an
advisory admission result: optional `Admissible`, typed `Rejection`
(`OrderErrorDetail` with a stable code label such as `BAD_QTY` and field violations), optional
resolved base quantity, optional `ProtectedPriceBound`, and `EvaluatedAtMs`.
Fee/quote estimates are no longer returned; CreateOrder always re-evaluates
the intent. Preview is not deployed on every API host, so handle an
unimplemented/not-found response and do not make Preview a prerequisite for
order submission. Create results expose `ResolvedBaseQtyScaled` and, for
quote-budget orders, `SubmittedMaxQuoteDebitScaled`.

Order reads carry exact execution totals as unsigned decimal integer strings,
never floats. `Order.AvgPriceE18` is the average execution price scaled by
1e18 (`Order.AvgPrice()` formats it, `"0"` with no fills); `AvgPx` keeps the
same average rounded down to 1e-9. `Order.CumNotional` is the fills' quote
amount before fees, scaled by 10^(9 + the pair's base quantity scale)
(`CumQuote(baseScale)` formats it). `Order.FeeTotal` (`AmountE18` at 18
decimals in `FeeAsset`, `IsRebate`, `Qty`) is set on order history and
single-order reads with execution history, nil on open-order reads and
stream updates. For a buy sized by a quote amount, `QuoteUsed(baseScale)` and
`QuoteUnspent(baseScale, quoteScale)` say how much of the amount the fills
used, fee included, and how much was left; both report false until
`FeeTotal.Qty` equals `CumQty`, because a fill's fee is recorded shortly
after it executes. Each fill settles its quote rounded down to 18 decimals, so
`CumNotional`, `CumQuote` and `QuoteUsed` are exactly what the fills settled
when the pair's base quantity scale is at most 9; above that they can exceed
the settled quote by less than 1e-18 per fill. A quote-amount buy that spent its amount ends `filled`;
`market_remainder` and `ioc_remainder` cancels mean the book or the price
limit stopped it first.

```go
baseScale, _ := client.Catalogs.BaseQuantityScaleForSymbol(symbol)
quoteScale, _ := client.Catalogs.QuoteQuantityScaleForSymbol(symbol)
detail, err := client.Orders.Get(ctx, nil, models.OrderKeyByID(orderID), nil, false, false)
if used, ok := detail.Order.QuoteUsed(baseScale); ok {
	unspent, _ := detail.Order.QuoteUnspent(baseScale, quoteScale)
	fmt.Println("used", used, "unspent", unspent)
}
```

An attached trailing stop's `LimitPrice` is checked before sending on
creates, previews and batch creates, and refused with the server's code and
violation on `order.attached_risk.trailing_stop.limit_price_ticks`: set on a
buy parent `ERROR_CODE_BAD_PRICE` (`sell_unset`), missing or zero on a sell
parent `ERROR_CODE_TRIGGER_BUY_REQUIRES_LIMIT` (`buy_required`), below
`ActivationPrice` `ERROR_CODE_BAD_PRICE` (`buy_at_least_activation`). Modify
and batch replace send a positive one as given; the server applies the side
rule and answers `ERROR_CODE_BAD_PRICE` with no violation. They refuse a zero or
negative one before sending, with `ERROR_CODE_TRIGGER_BUY_REQUIRES_LIMIT`
(`buy_required`) on `new_attached_risk.trailing_stop.limit_price_ticks`: leave
`LimitPrice` nil when the parent order buys.

Market orders are IOC and enforce a slippage-derived execution boundary. See
[Market Order Price Protection](https://polyester.com/docs/developer-docs/shared-concepts/market-order-price-protection)
before overriding pair defaults. Set at most one of `MaxSlippageBps` or
`MaxSlippageTicks` on a market `CreateOrderRequest`. `MaxSlippageBps` is 1–10000
for a buy and 1–9999 for a sell: a 100% cap would leave a sell no positive
price. An attached trailing stop takes 1–9999 on either side. Omit both to keep
the pair default. The fields are rejected on limit orders and if both are
supplied. `PairConstraints.MaxQuoteSlippage` is the largest absolute cap
`MaxSlippageTicks` accepts.

### Batch replace reconciliation

`Orders.BatchReplace` modifies up to 20 orders on one pair, each admitted or
rejected on its own, and returns admission, not execution finality. Each item
amends or replaces its order. An item that keeps the order's price, does not
raise its total quantity and keeps its client order ID amends the order in
place, under the same order ID and with its queue priority kept. A new price, a
larger total quantity or a new client order ID replaces the order with a
successor under a new order ID, with its queue priority reset. A new total
quantity at or below the filled quantity ends the order at its filled
quantity, with no successor.

Persist the returned `BatchRequestID`, then call `Orders.WaitBatchReplace`. It
polls `Orders.GetBatchReplaceStatus` (50 ms, doubling up to 500 ms) until no
item is `admitted`, that is until each is `working`, `rejected` or `terminal`,
and returns that status; `working` only means the order is live. A batch's
status can read not found for a few seconds after admission, so the wait polls
through not found and `UNAVAILABLE`.
`models.IsBatchReplaceSettled` tests the same condition on one status read.
An item can be admitted and then refused when applied, for example a post-only
order moved to a price that would cross: it reads `rejected`, changed nothing,
and its order keeps `OldOrderID` with its previous price and quantity.
`Code` is the refusal as sent (`POST_ONLY_CROSS`), and `ErrorCode` is the
`orders.v1` name a single modify returns (`ERROR_CODE_POST_ONLY_CROSS`; a code
newer than the SDK is kept as sent). The admission counts still count such an
item as accepted.

The admission answer's `ReplacementOrderID` is the planned successor, not proof
of an order: only a status item's `ReplacementOrderID` or an order read
confirms one. The status is kept for 60 seconds from acceptance. When that
window ends with an item still `admitted`, `WaitBatchReplace` returns the last
status and `*errors.BatchReplaceWindowExpiredError`, even when a status read is
still in flight; a later status read proves nothing, so reconcile the orders
with order reads. Cancel `ctx`, or give it an earlier deadline, to stop
waiting sooner: that returns `ctx.Err()`. Reuse the same caller-owned
`requestID` when retrying the same logical batch after an ambiguous failure.

```go
admitted, err := client.Orders.BatchReplace(ctx, nil, items, "BTC-USDT", nil, &requestID)
if err != nil {
	return err
}
status, err := client.Orders.WaitBatchReplace(ctx, nil, admitted.BatchRequestID, nil)
for _, item := range status.Items {
	if item.Phase == "rejected" {
		log.Printf("item %d refused: %s", item.ItemIndex, item.ErrorCode)
	}
}
```

Admitted and status items carry `ActionTaken`: `replaced` when a successor
took the order's place, or `amended` when the order kept `OldOrderID` (amended
in place, or ended at its filled quantity). For an amended item keep tracking
`OldOrderID`.
A replacement order's `InheritedCumQty` is the filled quantity it inherited
from its predecessors; `CumQty` minus `InheritedCumQty` is what that generation
executed.

A create rejected with `ERROR_CODE_CONFLICT_DUPLICATE_CLIENT_ORDER_ID` names
the order already holding the client order ID, when the server knows it:
`APIError.ExistingOrderID` for `Orders.Create`, and
`BatchCreateResultItem.ExistingOrderID` for a rejected batch item (empty for a
duplicate within the same batch). Read it with `Orders.Get`.

Your API key needs a policy that allows trading. Spot orders spend **trading**
balance (see below).

## User trade fees

`UserTrade` fee fields are fixed **18-decimal** magnitudes of `FeeAsset`
(`FeeAmountE18`, `ReferralShareAmountE18`), not catalog asset-scaled integers.
Convert e18 → the fee asset's catalog scale before subtracting from a BUY fill's
base quantity.

Magnitudes are unsigned. Treat `FeeAmountE18` as a **debit** unless
`FeeIsRebate` is true (then it is a **credit**). Proto3 omits false, so the
rebate flag is sparse on the wire.

`client.Fees.GetSpotFeeRates` returns the account target's current effective maker/taker
percents per listed symbol (optional `symbolID` filter). That is the live effective-rate
surface, not a guaranteed quote of every future fill. The completed user-trade record still
owns the exact charge.

Rows also expose `ReserveFeeRatePercent`, `PostOnlyReserveFeeRatePercent`,
`NextChangeAt` and `Breakdown`. Size a buy limit order that pays its fee in
the quote asset with the reserve rate, using the post-only reserve rate for a
post-only order. A buy sized by a quote amount reserves at the lower of the
reserve and taker rates. Effective maker/taker rates apply to fills. Refetch rates at `NextChangeAt` when present. `Breakdown`
contains tier rates, a market multiplier, account discounts and a referral
discount. Optional components and times may be absent; absent account
discounts decode as an empty slice.

See the [contract migration notes](docs/contract-748066a.md) for the full
fee model and exact integer budgeting guidance.

`Trades.List(..., afterMatchID)` is a per-symbol cursor. When `afterMatchID` is
set, pass a display `symbol` or `symbolID`; the SDK fails closed if the symbol
cannot be resolved to a non-zero `symbol_id`.

## VIP, spot fees, and trading rate limits

Public catalog reads (`ListVIPTiers`) need no credentials. Effective spot fees
(`Fees.GetSpotFeeRates`) and account trading limits (`RateLimits.GetTradingRateLimits`) work

strings. Optional qualification metrics, timestamps, and next-tier thresholds stay omitted
when unset. `SettledVolumeQuality` and `AverageAopQuality` report how complete each rolling
30-day metric is (`complete`, `price_unavailable` or `incomplete_history`, with

(`TRADING_RATE_LIMIT_CLASS_PLACE` / `_CANCEL`). Rate-limit rules expose

```go
tiers, err := client.VIP.ListVIPTiers(ctx)
status, err := client.VIP.GetVIPStatus(ctx)
```

## Product changelog API

`client.Changelog` reads the product changelog published for the environment the
client points at (devnet, testnet, ...). It is public and read-only: it needs no API
key, and the server rate-limits it per client address.

- `ListPosts` returns one page of post summaries, newest first, with change counts by
  kind. `Posts` iterates over every page.
- `GetPost(ctx, slug)` returns one full post with its sections and changes. A slug is
  the post's coverage cutoff date, `YYYY-MM-DD`; a second or third post on the same day
  gets `-2` or `-3`. An unknown slug fails with `*errors.APIError` whose `Code` is
  `not_found`.
- `ListChanges` returns one page of changes across posts, each with its post slug,
  publication time and section heading. `Changes` iterates over every page. Filters
  on different fields combine with AND; values within one field combine with OR.
  `StartTime` is inclusive and `EndTime` exclusive; an `EndTime` not after `StartTime`
  fails with `*errors.ValidationError` (`invalid_argument`).
- `BreakingChangesSince(ctx, t)` and `ActionRequiredSince(ctx, t)` return every
  breaking or action-required change published at or after `t`, newest post first.

Categories, audiences and surfaces are lowercase labels with constants in `models`
(`models.ChangelogCategoryBreakingChange`, `models.ChangelogSurfaceAPI`, ...). A value
newer than this SDK reads as `unknown(<n>)` instead of failing. Surfaces include
`market_data`, `quickswap` and `rewards`, and `ChangelogSection.Surface` names the
product area a section covers (empty for a section tied to none, such as the changes
that need your attention). `ListChanges` accepts at most 10 surfaces. `Change.ID` is the
change's base58 public ID. The service returns `Unavailable` (`*errors.ServerError`)
while it is starting.

```go
for post, err := range client.Changelog.Posts(ctx, models.ListChangelogPostsOptions{}) {
    if err != nil {
        return err
    }
    fmt.Println(post.Slug, post.Title, post.BreakingChangeCount)
}
post, err := client.Changelog.GetPost(ctx, "2026-09-24")
breaking, err := client.Changelog.BreakingChangesSince(ctx, time.Date(2026, 9, 1, 0, 0, 0, 0, time.UTC))
for _, entry := range breaking {
    fmt.Println(entry.PostSlug, entry.Change.ID, entry.Change.Title, entry.Change.MigrationGuidance)
}
```

## Triggers

`Triggers.List(..., status, ...)` filters by lifecycle status. Valid values:

`created`, `armed`, `running`, `completed`, `cancelled`, `failed`, `paused`

Unknown values return an error (they do not silently return an empty list).
Response `Status` uses the same labels (British spelling `cancelled`).

`Triggers.Get` and `Triggers.List` retry `UNAVAILABLE` (HTTP 503) and `DEADLINE_EXCEEDED` with the
same request: 25 ms, doubling up to 500 ms, for about 2 s, then return the
error. Once `Modify`, `Pause` or `Resume` has answered, these reads return the
trigger as changed, or `UNAVAILABLE` until they can, so a read right after the
change never returns its previous state.

A market halt cancels the market's open orders with `CancelReason`
`market_halted` and ends its open triggers with `CancelReason` `market_halted`.
An order the halted market refuses after admission ends `REJECTED` with
`RejectReason` `MARKET_HALTED`. A trigger it refuses after admission ends
`failed` with `FailureReason` `market_halted`, as do the attached legs of an
order refused this way; a fire it refuses while the trigger stays live is a
`fire_refused` event with `FireRefusalReason` `market_halted`.

`Orders.Get(..., includeAttachedRisk)` returns policy data on
`Order.AttachedRisk`. `Order` also exposes `PostOnly`. With
`includeAttachedRiskState=true`, runtime legs remain available even when
`includeAttachedRisk=false`; absent policy fields stay zero/empty.

```go
oco := &models.AttachedRiskInput{
    TakeProfit: &models.RiskLegInput{TriggerPrice: models.PriceFromDecimal("72000")},
    StopLoss:   &models.RiskLegInput{TriggerPrice: models.PriceFromDecimal("58000")},
    OCO:        true,
}
created, err := client.Orders.Create(ctx, models.CreateOrderRequest{
    Symbol: &symbol, Side: "buy", OrderType: "limit",
    Qty: models.QtyFromDecimal("0.001"), Price: &price, AttachedRisk: oco,
}, nil)
```

Each leg watches the last traded price by default. Set `TriggerPriceSource`
to `"index"` on a `RiskLegInput` or `TrailingStopInput` to watch the market's
index price instead; on a market without an index price the order is
rejected. Reads report the source with the same labels (`"last"`,
`"index"`), so a leg read back can be sent again unchanged.

```go
// created.TakeProfitTriggerID, created.StopLossTriggerID
_, err = client.Orders.ModifyWith(ctx, nil, services.ModifyParams{
    Symbol: symbol, Key: models.OrderKeyByID(created.OrderID),
    NewAttachedRisk: &models.AttachedRiskInput{
        TakeProfit: &models.RiskLegInput{TriggerPrice: models.PriceFromDecimal("74000")},
        StopLoss:   &models.RiskLegInput{TriggerPrice: models.PriceFromDecimal("57000")},
        OCO:        true,
    },
})
```

Standalone `trailing_stop` creates accept `side` `sell` or `buy`. A sell
trails the highest price since arming (`Details.PeakPrice`) and fires on a
fall; a buy trails the lowest (`Details.TroughPrice`) and fires on a rise. A
buy requires `limitPrice`, its maximum price: the most the child pays per
unit, which also sizes the funds set aside for it. It must be at least the
activation price, or the price it watches when there is none, and a rise
that fires above it still fires, with the child filling only at or below
it. A sell refuses `limitPrice`.

```go
maxPrice := models.PriceFromDecimal("65000")
distanceBps := int32(100) // 1%
trigger, err := client.Triggers.Create(ctx, nil, "BTC-USDT", "trailing_stop",
	nil, "buy", models.QtyFromDecimal("0.01"), "market", &maxPrice, "", "",
	nil, nil, false, codecs.CreateTriggerOptions{TrailingDistanceBps: &distanceBps})
```

Stop-loss, take-profit and trailing-stop creates take `triggerPriceSource`:
`"last"` (the default when empty) watches the last traded price and
`"index"` the market's index price, where a market without one fails the
trigger with `index_price_unavailable`. It is fixed at create and reads back
as `Details.TriggerPriceSource`.

List/get projections use the wire side (attached trailing stops may be buy
or sell, opposite the parent); a buy's maximum price reads back as
`Trigger.LimitPrice`. Attached triggers expose `ParentOrderID` when present.

Stop-loss and take-profit triggers on either side may use a market or a
limit child. A market child accepts an optional slippage cap, either
`MaxSlippageTicks` or `MaxSlippageBps` in `CreateTriggerOptions`: it fills
only within that cap of the price that fired it, and a buy reserves its funds
at the trigger price raised by the cap. Without a cap the pair's default
market slippage applies. Setting both, or a cap on a limit child, is refused.
A buy market child accepts 1 to 10000 bps; a sell, and a trailing stop on
either side, 1 to 9999. Get, list and the trigger stream expose the cap as
`Trigger.MaxSlippage` / `Trigger.MaxSlippageBps`.

```go
triggerPrice := models.PriceFromDecimal("58000")
capBps := int32(50) // 0.5%
stop, err := client.Triggers.Create(ctx, nil, "BTC-USDT", "stop_loss",
	&triggerPrice, "sell", models.QtyFromDecimal("0.01"), "market", nil, "", "",
	nil, nil, false, codecs.CreateTriggerOptions{MaxSlippageBps: &capBps})
```

`Triggers.ListEvents` returns the same not-found error as `Triggers.Get`
for an unreadable trigger. It retries catching-up `UNAVAILABLE` responses
with the same bounded policy and request as trigger reads.

A trailing stop created with an activation price the market has already
reached now ends `FAILED` with reason
`TRIGGER_FAILURE_REASON_TRIGGER_WOULD_TRIGGER_IMMEDIATELY` (244).
`ModifyTrigger` and order modifies that would make it act at once are refused
with `ERROR_CODE_TRIGGER_WOULD_TRIGGER_IMMEDIATELY` (302), leaving the
existing state unchanged. To start trailing from the market, clear the
activation price with a present zero.

When modifying a trigger, omit `ActivationPrice` / `MaxSlippageTicks` /
`MaxSlippageBps` to preserve the current values. The cap of a trailing stop or
of a market-child stop-loss or take-profit can be changed; a cleared cap on a
market child falls back to the pair default. A child's limit price is fixed
at create: cancel the trigger and create a new one to change it. Send an explicit zero
(`PriceFromTicksInt(0)` or `*int32(0)`) to clear an existing activation
price or maximum-slippage cap. Modify `MaxSlippageBps` must be 1–9999 (the
patch does not say which leg it changes, so it takes the sell and trailing-stop
cap; a buy market child's 10000 is set at create) and still accepts `0` to
clear.
Create/modify `TrailingDistanceBps` must be 1–10000; zero does not clear a
trailing distance. `Triggers.Modify` and `Triggers.Resume` take an optional
symbol: pass nil for both `symbol` and `symbolID` to target the trigger's own
market, or set one, which must be that market. An API key limited to specific
markets must still pass it. A trailing stop's `Details.TriggerPrice` is its
current threshold once armed; it moves with the peak or trough. Ladder creation requires the resolved minimum price ticks
to be strictly less than the maximum.

`Orders.ListOpen` / `Orders.ListHistory` accept an optional trailing
`triggerID` to return only child orders created by that trigger (TWAP/ladder
slices). Trigger-event `FirePrice` is empty for time-scheduled TWAP slice fires
(`fire_price_ticks` is optional on the wire). Terminal triggers/events expose
typed `CancelReason` / `FailureReason` labels (empty when the proto oneof is
unset or unspecified).

A trigger's events include `fire_refused`: a fire whose order was refused
while the trigger stayed live. It is not terminal, so the trigger keeps its
`armed` or `running` status; read `Trigger.Status` rather than inferring it
from the last event. `FireRefusalReason` says why, with the `FailureReason`
labels: `market_halted` or `post_only_cross` (it waits for the next price
through its trigger price), `min_notional`, `min_quantity` or `step_size`
(the order would have been below the market's minimum; it fires again once
the position changes), `rate_limited` or `account_repairing` (it fires again
shortly), or `self_trade_prevented` (self-trade prevention expired an
attached exit's order against another of the account's resting orders; it
fires again at a new trade at or beyond its trigger price, or once that order
is gone or no longer at the best price). `ChildSeq` is the refused attempt, so
a later `fired` event names a higher one. For `self_trade_prevented` that
attempt placed an order, canceled with `stp_expire_taker` or
`stp_expire_both`; for every other reason it placed none. A refusal that ends the trigger is still
a `failed` event with `FailureReason`. `Triggers.ListEvents` filters on
`fire_refused`, and an event type or reason newer than this SDK reads as
`unknown(<n>)`.

`TriggerEvent.EventType` is `fired`, `canceled`, `updated`, `failed`,
`activated` (a trailing stop started tracking), `armed` (an attached
take-profit, stop-loss or trailing stop started protecting its parent's filled
quantity, once) or `fire_refused`. A ladder has no event types of its own: read
its `Trigger.Status`, `completed`, `canceled` or `failed`. A completed ladder
may not have filled: read its executed quantity and levels.

A trigger change that names a listed pair other than the trigger's own is
refused with `ERROR_CODE_TRIGGER_SYMBOL_MISMATCH` (305). Nothing changed: name
the trigger's own pair or omit the symbol. A pair that is not listed is
`ERROR_CODE_UNKNOWN_SYMBOL`. A balance or other ledger read given a zero or
malformed sub-account ID is refused with the ledger code
`ERROR_CODE_INVALID_SUBACCOUNT_ID` (11), read from `APIError.Code`.

`Trigger.Version` is 1 for a trigger's first state and higher for every later
state change. Across list reads and realtime updates, keep the copy with the
highest version and ignore one whose version is not higher than the copy you
hold. It is 0 from a server that predates trigger versions.

## Balances: funding vs trading

Ledger balances have separate **funding** and **trading** buckets per asset.

- An external deposit can stop in **funding** or continue to **trading**,
  depending on its configured route.
- Spot orders spend **trading** balance.
- Move funds funding → trading in the Polyester UI (**Funding → Unified Trading**)
  or on-chain via the funding wallet.

SDK notes:

- **Funding → trading:** on-chain `TradingGateway.deposit` (not an API-key RPC).
  Package `github.com/Fabric-Labs/polyester-sdk-go/chain` encodes calldata and can
  submit UserOps: pass an owner EOA private key to `NewSmartAccount` (SDK derives
  the Polyester Safe; no UI-exported owner key).
- **Funding → external:** on-chain `FundingAccount.withdrawToChain` (same `chain` package).
- **Funding → another user's funding wallet:** on-chain `FundingAccount.UAssetTransfer`
  via wallet/smart-account signing in the Polyester app (not an API-key RPC).
- **Trading → funding:** `client.TradingWithdraws.CreateToFunding(...)` with a
  signed intent payload.
- **Trading → external destination check:**
  `client.TradingWithdraws.ValidateDestination(ctx, chainID, address)` returns
  user-safe `valid` / `code` / `message` / `canonical_destination_address`
  without creating a withdraw (create RPCs remain authoritative).
- **Trading → trading (another account):** `client.InternalTransfers.Create(...)`.

API-key withdrawals always use the authenticated key's bound account or
subaccount. The SDK's default subaccount does not change that source.
`CreateToFunding` and `CreateToExternalChain` reject explicit `account` or
`subAccountID` arguments; pass `nil` for both and use a key bound to the
intended source. `CreateWalletTradingWithdraw` supports explicit account
selection and the configured default subaccount for wallet/JWT withdrawals.

```go
account, err := chain.NewSmartAccount(ownerPrivateKeyHex, nil, nil)
call, err := chain.EncodeTradingGatewayDeposit(
    chain.PolyesterDevnetEnvironment.Contracts.TradingGatewayAddress,
    uAssetID, quantityScaled,
)
receipt, err := account.SendCalls([]chain.ChainCall{call}, true, 60*time.Second)

// Funding → external: QuoteZipperFee + EncodeFundingWithdrawToChain
// Whitelist toggles / destination entries / GuardRegistry signer setup:
// EncodeAddAllowedExternalDestinations, EncodeSetInternalAccountAllowlistRequired, …
```

Realtime delivery: bounded queues fail with `QueueOverflowError` instead of
silently dropping. Use `SetOnError` and check `Err()` after `Messages()` closes.
Reconnects use capped exponential backoff with per-subscription jitter.
Orderbook `CreateSubscriptionOptions` exposes `OnSequenceGap`, `OnReconnect`,
`OnSnapshotRefresh`, and `OnError`. Managed create methods wait for both the
WebSocket handshake and initial snapshot before returning.

Pass `DefaultAccountID` (your Profile **Account ID**) on the client for bucket
transfers and other account-scoped ledger operations.

## Public market data

Public endpoints do not require an API key. Authenticated endpoints use the
credentials above.

```go
symbol := "BTC-USDT"
candles, err := client.MarketData.GetCandles(ctx, &symbol, nil, "1m", 50, nil, nil, false)
current, err := client.MarketData.GetCurrentCandle(ctx, &symbol, nil, "1m")
trades, err := client.MarketData.GetTrades(ctx, &symbol, nil, 20, nil)
// Gap-free backfill, ascending by match ID: start at "0", then pass each
// page's NextAfterTradeID; when it does not move, retry later with backoff.
page, err := client.MarketData.GetTradesAfter(ctx, &symbol, nil, "0", 1000)
_ = page.NextAfterTradeID
_ = candles
if current != nil {
	_ = *current
}
_ = trades

sub, err := client.MarketData.SubscribeTrades(ctx, &symbol, nil)
if err != nil {
	log.Fatal(err)
}
defer sub.Close()
sub.SetOnError(func(err error) {
	log.Printf("realtime interruption: %v", err)
})
for trade := range sub.Messages() {
	fmt.Println(trade.Price.Ticks(), trade.Qty.Scaled())
	break
}
if err := sub.Err(); err != nil {
	log.Printf("realtime ended: %v", err)
}
```

Public trades, user fills (`Trades.Subscribe`), ledger transfers
(`Transfers.Subscribe`) and trigger events (`Triggers.SubscribeEvents`) arrive
from the server in batches; each subscription emits every event of a batch, in
order, as its own message. A repeated identity replaces the earlier copy:
`(MatchID, OrderID)` for a fill, `(TransferID, AccountCode, IsDebit)` for a
transfer leg, and `(TriggerID, EventType, ChildSeq, TsNs)` for a trigger event.
`LedgerTransfer.TransferID` is the unsigned 128-bit decimal ID both legs of a
transfer share.

`GetCandles` returns rows newest-first. With incomplete candles enabled, the
open candle is prepended; `GetCurrentCandle` therefore returns the first row, or
`nil` when no candle rows exist.

## Realtime

Realtime is binary-only. Centrifugo channels negotiate the `centrifuge-protobuf`
WebSocket subprotocol, send binary length-delimited Centrifugo commands, and
decode protobuf publication payloads from `:proto` channels. ConnectRPC's
optional JSON wire mode does not apply to realtime. Incoming WebSocket messages
and protobuf record/field lengths are capped at 8 MiB.

### Live orders

`Orders.Subscribe` streams an account's orders over the private WebSocket
(`/v1/ws/private` on the API host, `wss://` for `https://`, subprotocol
`polyester.v1.proto`). Orders decode to the same `models.Order` as the order
reads. Events arrive on `Messages()`; switch on their type:

```go
import (
	"github.com/Fabric-Labs/polyester-sdk-go/models"
	"github.com/Fabric-Labs/polyester-sdk-go/realtime"
)

sub, err := client.Orders.Subscribe(ctx, nil) // nil: the client's DefaultAccountID
if err != nil {
	log.Fatal(err)
}
defer sub.Close()

orders := map[string]models.Order{}
ready := false
for event := range sub.Messages() {
	switch e := event.(type) {
	case realtime.OrderStreamConnected:
		log.Print("order stream connected")
	case realtime.OrderSnapshot:
		// The full live view: replace local state.
		clear(orders)
		for _, o := range e.Orders {
			orders[o.OrderID] = o
		}
	case realtime.OrderReady:
		// Everything acknowledged before the subscribe is now reflected:
		// an order missing from `orders` can be trusted to be gone.
		ready = true
	case realtime.OrderUnit:
		for _, o := range e.Orders {
			if cur, ok := orders[o.OrderID]; !ok || o.Version > cur.Version {
				orders[o.OrderID] = o
			}
		}
		for _, id := range e.RemovedOrderIDs {
			delete(orders, id) // left the live view; not a cancellation
		}
		for _, ev := range e.Events {
			if ev.Order != nil && ev.Order.Fill != nil {
				fmt.Println("fill", ev.Order.OrderID, ev.Order.Fill.MatchID)
			}
			if ev.Outcome != nil {
				fmt.Println("command answered", ev.Outcome.Kind, ev.Outcome.Reason)
			}
		}
		// Before ready, an order absent from the map may still exist.
		fmt.Println("live orders", len(orders), "complete", ready)
	case realtime.OrderStale:
		// With reason order_unavailable only e.OrderIDs are behind.
		log.Printf("account view stale=%v %s %v", e.Stale, e.Reason, e.OrderIDs)
	case realtime.OrderStreamDisconnected:
		ready = false // until the replacement subscription reports OrderReady
		log.Print("order stream disconnected; resuming")
	case realtime.OrderStreamError:
		log.Printf("order stream error: %v", e.Err)
	}
}
if err := sub.Err(); err != nil {
	log.Printf("order stream ended: %v", err)
}
```

- **Snapshot, then units.** A snapshot is installed whole, after its last
  page. Each unit is one change: the changed orders (complete), removed order
  IDs, and the events that caused it (accepted, filled with the fill, canceled,
  rejected, replaced, attached risk) plus answers to commands that changed no
  order (amend, cancel or replace rejected, rejected, cancel-all done). Keep
  the copy of an order with the higher `Version`; equal versions are identical.
- **End reasons.** Orders carry `RejectReason` and `CancelReason` as the
  order reads do. A rejected event's `RejectReason` and a canceled event's
  `CancelReason` use the same labels; the replaced event of the order a
  replace ended has `CancelReason` `replaced` and its `ReplacementOrderID`.
- **Ready.** `OrderReady` comes once the stream reflects at least every
  acknowledgement given before the subscribe, including every order read
  made before it. Wait for it before trusting that an order missing from the
  stream does not exist. To combine with a REST read: read open orders,
  subscribe, wait for `OrderReady`, then merge both by `Version` (the higher
  wins). It comes once per server subscription, so again after each
  resubscribe or reconnect; a subscription that joins an account already
  ready gets it right after its `OrderSnapshot`.
- **Resume.** Sequence gaps, expiring connect and subscribe tokens, heartbeat
  loss (3 s) and reconnects (0.5 s doubling to 10 s, with jitter) are handled
  for you, resuming from the last applied position. When the server cannot
  resume, a new `OrderSnapshot` replaces the state; the events in between are
  not delivered, and fills stay readable from trade history. A resubscribe the
  server does not confirm within 30 s reports `OrderStreamError` and tries again
  with backoff.
- **Sharing.** One connection carries every account of the client, and
  subscriptions of the same account share one server subscription. A later
  subscription starts from the current state.
- **Ending.** The stream ends, closing `Messages()` with `Err()` set, when the
  server refuses the subscription (`RealtimeError.Code`, for example
  `FORBIDDEN`), when it does not confirm a new subscription within 30 s, when
  the API key is refused, on close codes 4400 and 4403
  (`RealtimeError.CloseCode`), or with `QueueOverflowError` when the consumer
  falls behind. `Close` (or canceling `ctx`) stops it; after the last
  subscription closes, `Close` returns once the connection and its
  goroutines have stopped.

Order quantities are raw scaled integers, and `order.OrigQty.Scale()`,
`order.CumQty.Scale()`, and `order.LeavesQty.Scale()` may be `nil`. Bots must
resolve the base quantity scale from hydrated catalogs using `order.SymbolID`
before formatting or reusing a quantity. Never invent a fallback scale.

### Subscriptions the server ends

When the server ends a realtime subscription, `Messages()` delivers what is
queued and closes, and `Err()` and the error callback report
`*errors.SubscriptionEndedError` with the channel, the server's code and text,
and `Reason`. The exception is a sub-account's balances, transfers, trades,
triggers or lifecycle channel: the server can end one of those after access was
granted again, so the SDK reads `ListSubaccounts` and, while the sub-account is
listed with a role, subscribes again with a fresh token. `Resubscribes()` and
`TakeResubscribed()` report the gap. It stops, with the reason, when a
`removed` update for that sub-account arrived on this client, when the list no
longer has it, when the list or the token is refused (`Cause` holds the
refusal), or after 6 attempts that did not stay up for a minute. Requests are
paced across the client, so many subscriptions ending together share one list
read per second and at most five attempts per second. An API key bound to a
sub-account sees that sub-account in the list; a root key cannot subscribe to a
sub-account's channels.

### Managed snapshot-then-stream

Snapshot retries retain buffered publications until a successful refresh merges
them exactly once. Recovery-buffer overflow fails closed, and `Close` cancels
in-flight refresh work and the replacement socket.

```go
import "github.com/Fabric-Labs/polyester-sdk-go/services"

ob, err := client.Orderbook.CreateSubscription(ctx, services.CreateSubscriptionOptions{
	Symbol: "BTC-USDT",
	Depth:  50,
})
if err != nil {
	log.Fatal(err)
}
defer ob.Close()
ob.SetOnError(func(err error) {
	log.Printf("managed order book failed: %v", err)
})

for book := range ob.Updates() {
	fmt.Println(book.BookSeq, book.Available, len(book.Bids))
}
```

`OrderbookData.Available` is true when the book is current: its sides are its
levels, and an empty side means no liquidity. It is false while the market's
book is being built or after it was invalidated: its levels are unknown, not
empty, so request the snapshot again later (`Orderbook.Get`, or
`RefreshSnapshot` on a managed subscription) instead of reading empty sides as
no liquidity. A managed subscription carries its last snapshot's value and
requests an unavailable snapshot again by itself, after 1 s doubling to 8 s,
until the book is available or the subscription stops; repeated unavailable
answers add no update. Its first update is always the fetched snapshot. A
market whose book stays unavailable keeps being requested once every 8 s, so a
bot recovers by itself when the book comes back; close the subscription to stop.
An environment that does not serve this release yet reports false for every
book.

## Lifecycle transaction lookups

One chain transaction can reference multiple lifecycle flows when operations
are bundled. Transaction lookups therefore return a page, not one flow:

```go
page, err := client.Lifecycle.ListFlowsByTx(ctx, txHash, "any", 50, nil)
if err != nil {
	log.Fatal(err)
}
flowIDs := make([]string, 0, len(page.Flows))
for _, flow := range page.Flows {
	flowIDs = append(flowIDs, flow.IntentID)
}
for page.NextPageToken != "" {
	token := page.NextPageToken
	page, err = client.Lifecycle.ListFlowsByTx(ctx, txHash, "any", 50, &token)
	if err != nil {
		log.Fatal(err)
	}
	for _, flow := range page.Flows {
		flowIDs = append(flowIDs, flow.IntentID)
	}
}
```

`Lifecycle.GetFlowByTx` also returns the complete first page. Use
`Lifecycle.ListFlowsByTx` when following pagination.

## Transport

Connect RPC over HTTP via generated clients in `gen/`. Wire format defaults to
**binary protobuf**; set `Config.WireFormat` to `"json"` for debugging.

The Go SDK ships with a committed `gen/` tree. Proto stubs are updated when a new
`gen/` bundle is landed (same source as Python/Rust). You do not need local buf
generation for day-to-day SDK work.
